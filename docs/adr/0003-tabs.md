# Ship `Tabs` / `Tab` / `TabPanel` from the DS with derived accessibility ids

`@telicent-oss/ds` ships three exports — `Tabs`, `Tab`, `TabPanel` — wrapping `@mui/material`'s `Tabs` and `Tab` and adding the `TabPanel` that `@mui/material` does not have. Consuming apps import all three from `@telicent-oss/ds` and never write the `CustomTabPanel` / `a11yProps` pair from mui.com.

## Why the DS owns this

**1. `@mui/material` ships no `TabPanel`, so the docs ship a copy-paste.** MUI's Tabs page hands the reader a `CustomTabPanel` component and an `a11yProps(index)` helper to paste into their own codebase. `TabPanel` proper lives in `@mui/lab`, which is a pre-1.0 alpha. Any app that needs tabs therefore hand-rolls the accessibility wiring, and the second app to do it will do it differently — the drift ADR-0002 exists to prevent, and here it is visible before it happens rather than after. No Telicent app uses tabs at the time of writing; this port is deliberately ahead of first use.

**2. The copy-paste has an accessibility gap.** mui.com's `CustomTabPanel` sets `role`, `hidden`, `id`, and `aria-labelledby`, but no `tabIndex`. WAI-ARIA APG makes the panel a tab stop so a keyboard user can reach a panel whose content holds no focusable element. Every app that pastes the example inherits the gap, against ADR-0001.

**3. The id wiring is derivable, so no one should type it.** A tab's `id`, its `aria-controls`, its panel's `id`, and its panel's `aria-labelledby` are four strings determined by two facts: which tab set this is, and which tab it is. The DS takes those two facts (`idPrefix` and `value`) and derives all four.

## Decisions

**1. `idPrefix` on `Tabs` and on each `TabPanel`; ids are derived, never written.**
`Tabs` puts `idPrefix` on a private context, so each `Tab` child derives `id={prefix}-tab-{value}` and `aria-controls={prefix}-panel-{value}`. `TabPanel` renders as a sibling of `Tabs`, outside that provider, so it takes `idPrefix` as a prop and derives the mirror pair. Two strings at the callsite replace two hand-rolled helpers, and two tab sets on one page cannot collide.

**2. `Tab`'s `value` is required and narrowed to `string | number`.**
MUI falls back to the child's index when `value` is omitted; the DS requires it, because the value becomes part of a DOM id. Narrowing to `string | number` keeps an object value from stringifying into `[object Object]` and producing two identically-identified panels.

**3. An accessible name is required at the type level.**
`TabsProps` omits MUI's optional `aria-label` / `aria-labelledby` and re-adds them as a union requiring exactly one. An unnamed tablist does not compile. The DS cannot invent the name, so requiring it is the only way to guarantee it (ADR-0001).

**4. The panel element always renders; only its children are conditional.**
`hidden` toggles on the wrapper so the inactive tab's `aria-controls` always resolves to a real node. Children unmount by default — matching mui.com's behaviour and costing nothing for an unseen panel — and `keepMounted` holds them in the tree when the panel carries form state worth preserving across switches.

**5. `Tab` outside `Tabs` throws.**
`role="tab"` outside a `tablist` is invalid ARIA, and a silent fallback to unwired ids would leave exactly the gap this ADR closes. A thrown error at first render is louder and cheaper to diagnose.

**6. The tab-bar divider is a theme override, not an `sx` wrapper.**
mui.com's examples wrap `Tabs` in `<Box sx={{ borderBottom: 1, borderColor: "divider" }}>`. The DS puts the border on `MuiTabs`' root in `tabs-overrides.ts`, reading the colour from `theme.palette.divider` and moving it to the inline edge for `orientation="vertical"`. This is rung 4 of the palette-first ladder: the palette carries the colour but has no token for whether a border exists.

**7. No padding opinion inside the panel.**
mui.com's example wraps panel content in `<Box sx={{ p: 3 }}>`. Spacing between a panel and its surrounding layout is the app's, and baking a value in would be undone by `sx` at most callsites.

## Consequences

- Apps get tab navigation that passes WCAG 2.2 AA wiring by construction, with no `a11yProps` helper in app code.
- Three narrowings on MUI's surface: `value` required and `string | number`, an accessible name required, `hidden` owned by `TabPanel`. Everything else on `Tabs` and `Tab` passes through, and a callsite prop overrides a DS default because `{...props}` spreads last.
- `src/components/Navigation` becomes an exported category (`export * from "./components/Navigation"`). `Menu`, which also lives there, stays unexported.
- `@mui/lab` stays a devDependency and unused. No new runtime dependency.
- Tabs render the selected state as `primary.main` text plus a `primary.main` indicator. On four theme × mode combinations that colour fails contrast against `background.default` — GraphOrange light (1.93:1), DocumentPink light (2.65:1), DataNavy dark (2.25:1), Blank dark (1.25:1) — because `createLightPalette` / `createDarkPalette` fall back to the other mode's primary when a theme defines only one. Pre-existing and already live via `MuiMenuItem`'s `.Mui-selected`; Tabs make it more visible. Tracked as its own palette work, not fixed here.

## Considered alternatives

**Re-export `@mui/lab`'s `TabContext` / `TabList` / `TabPanel`** — the package is already a devDependency. Rejected: `@mui/lab` is `5.0.0-alpha.170`, so a DS-wide API would rest on a pre-release, and it would have to move to `dependencies`. `TabContext` also requires apps to wrap the tab set in a third component, which is a composition step to get wrong. Deriving four strings costs ~40 lines.

**Context for `TabPanel` too, via a wrapping provider** — a `TabsGroup` around both `Tabs` and its panels would remove `idPrefix` from the panels. Rejected: it adds a component apps must remember to wrap, and mis-nesting it fails silently. The same provider-ordering risk ADR-0002 moved inside the DS.

**A single composite — `<Tabs items={[{ label, value, content }]} />`** — one component owning both bar and panels, no ids at any callsite. Rejected: it fixes the panels' DOM position next to the tab bar, which rules out the common layout where the bar sits in a header and the panel fills the page. Available later as a composite built on these three.

**Ship `Tabs` and `Tab` only, no `TabPanel`** — theme the bar, leave panels to apps. Rejected: the panel is where the accessibility wiring and the copy-paste live. Bar-only would be the template-only option ADR-0002 rejected, for the same reason.

**Silent fallback when `Tab` renders outside `Tabs`** — omit the ids rather than throw. Rejected: it produces a tab set that looks right and is unwired, which is the failure this ADR exists to make impossible.
