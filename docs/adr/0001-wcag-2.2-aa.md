# Target WCAG 2.2 AA, not AAA, as the design system's conformance level

We commit `@telicent-oss/ds` to **WCAG 2.2 AA** as the level our components must satisfy. Compliance is *surfaced* through the Storybook a11y panel (via `@storybook/addon-a11y`); it is not enforced by CI at this stage. We explicitly do *not* target AAA as a system-wide conformance level. AAA remains available as an aspirational, per-criterion overlay documented in `docs/accessibility.md`.

## Why not AAA — what WCAG itself says

WCAG's own guidance is unambiguous on this. From the [W3C Understanding WCAG 2.2 — Conformance Requirements](https://www.w3.org/WAI/WCAG22/Understanding/conformance):

> "It is not recommended that Level AAA conformance be required as a general policy for entire sites because it is not possible to satisfy all Level AAA Success Criteria for some content."

WCAG defines three conformance levels and intends them to be used differently:

- **Level A** — the minimum. Content that fails A is unusable for some users.
- **Level AA** — the working target for most public and commercial products. This is what UK PSBAR (Public Sector Bodies Accessibility Regulations), EN 301 549, and the US Section 508 refresh all require.
- **Level AAA** — the highest standard, designed as a **menu of individual criteria to adopt where feasible**, not a whole-system commitment. WCAG is explicit that many AAA criteria conflict with legitimate design and content patterns.

The intended use pattern for AAA is: pick the individual AAA criteria that make sense for your specific content, apply them there, and document what you conform to. Not: turn on all AAA criteria across a design system that must serve many kinds of application.

## Why AAA would be actively harmful as a DS-wide target

Adopting AAA globally would either force us to remove useful patterns or make dishonest conformance claims. The AAA criteria that would specifically bite a component library:

| Criterion | AA rule | AAA rule | Impact if adopted |
|---|---|---|---|
| **1.4.6 Contrast (Enhanced)** | 4.5:1 normal, 3:1 large | **7:1 normal, 4.5:1 large** | Guts brand themes. Orange or green accents on dark greys almost never reach 7:1. Would remove `GraphOrange`, `GeoGreen`, and constrain future themes. |
| **2.5.5 Target Size (Enhanced)** | 24×24 CSS px (2.2 AA) | **44×44 CSS px** | Removes small `IconButton` variants, chip delete icons, dense toolbar buttons. Data-heavy views (maps, tables) rely on smaller targets. |
| **2.2.3 No Timing** | Timing must be adjustable | **No time limits at all** | Kills `Snackbar` auto-dismiss and every timed feedback pattern. |
| **3.3.6 Error Prevention (All)** | For legal / financial / data submissions | **All submissions** must be reversible, checked or confirmed | Blocks instant-save patterns and inline edits. |
| **2.4.9 Link Purpose (Link Only)** | Purpose clear from context allowed | Link text alone must explain destination | Bans "read more" and "click here" patterns even with clear surrounding context. |

The single blocker is **1.4.6**. Even if all other AAA criteria were achievable, hitting 7:1 contrast across the current theme palette would require redesigning the brand colours.

## Why the automated AAA delta would be near-empty even if we tried

We ran an informal AAA scan against 10 representative primitives before writing this ADR. With all `wcag2aaa`, `wcag21aaa`, and `wcag22aaa` tags enabled, axe-core produced **zero additional findings** over the AA baseline in a jsdom environment.

The reasons are technical, not a reflection of the DS's real AAA-readiness:

1. **`color-contrast-enhanced`** (7:1) — the single most impactful AAA rule — cannot run in jsdom. This is the finding that would matter, and no static analyser can produce it without a browser.
2. **Focus appearance (2.4.13), timing (2.2.3), no-interruptions (2.2.4), link purpose (2.4.9), error prevention (3.3.6), redundant entry (3.3.7)** — axe cannot automate these at all. They require human judgement or contextual understanding.
3. **Target size enhanced (2.5.5)** — axe does not implement a 44×44 rule variant.

So adding AAA tags to a CI blocking check would cost real test time and produce no signal. It is not a useful thing to do.

## How AAA should still influence us (the intended use pattern)

Consistent with WCAG's own guidance, we adopt AAA criteria **individually where they are cheap and non-regressive**, and document the result. Concretely:

- **2.4.13 Focus Appearance** (AAA) — buy this by default. A visibly strong focus ring costs almost nothing and materially improves keyboard usability. This should become a DS-wide standard even though we don't claim AAA overall.
- **Contrast** — publish a per-theme conformance table in `docs/accessibility.md`. Some theme + mode combinations may hit 7:1 for some tokens; document which do, so consumers with AAA requirements can select a compliant configuration.
- **Small `IconButton` variant** — document the target-size AAA gap; consumers requiring 44×44 targets should avoid the small variant.
- **Auto-dismissing feedback** — document the timing gap; consumers requiring AAA should use a variant that requires explicit dismissal (existing or new).

The result is a system that **conforms to AA** and **exposes AAA-clean configurations** where they happen to exist, without falsely claiming a level it cannot deliver.

## Consequences

- `docs/accessibility.md` declares WCAG 2.2 AA as the target policy and documents the intentional AAA gaps listed above, so consumers building AAA-requiring applications can make informed choices.
- `@storybook/addon-a11y` is installed and configured with tags: `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, `best-practice`. AAA tags are not included.
- Violations are surfaced by the a11y panel in Storybook for developers to see while authoring or reviewing stories. There is no CI gate at this stage.
- Manual AAA review, if undertaken, uses the same Storybook panel in a real browser. Output feeds the AAA table in `docs/accessibility.md`, not a CI check.
- Escalation to a CI gate is possible additively (install `@storybook/addon-vitest`, flip `parameters.a11y.test` from advisory to `'error'`); this ADR does not commit to it.

## Considered alternatives

- **Target AAA globally.** Rejected: WCAG advises against it; 1.4.6 makes it infeasible with the current brand palette; adds testing cost with near-zero signal.
- **Advertise AAA but silently violate the criteria we can't meet.** Rejected outright: dishonest.
- **Enforce 2.2 AA as a blocking CI check from day one.** Deferred: we chose to start with an advisory panel (Storybook only) to size the debt in practice before committing to CI enforcement. This can be added later without touching this ADR.
- **Add an informational AAA scan to CI.** Rejected: adds test-suite time and produces no findings that AA doesn't already cover in a headless environment. Any real AAA finding requires a browser (contrast) or a human (focus, timing, purpose).
